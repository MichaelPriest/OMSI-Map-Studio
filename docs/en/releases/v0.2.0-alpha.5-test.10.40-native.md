# OMSI Map Studio v0.2.0-alpha.5-test.10.40-native

Native preview focused on the viewport reload race after automatic road generation.

## Addressed problem

OSM generation was already completing and persisting roads/junctions, but the viewport could still process overlapping snapshots. The previous path allowed `LoadSceneAsync` to mutate global scene state before asset loading had finished and, because it used `ConfigureAwait(false)`, the D3D11 geometry rebuild/upload could resume outside the UI caller context.

This created a window where:

- two `SetMapSnapshotAsync` calls could overlap;
- an older reload could complete after a newer reload;
- global scene state could point to one snapshot while assets belonged to another;
- renderer buffers could be rebuilt while another WinUI path was still rendering;
- road pieces could look temporarily missing/disconnected even though they were persisted correctly.

## Fix

- `SetMapSnapshotAsync` is now serialized through a gate with a **latest-wins** policy;
- a newer snapshot cancels/coalesces the older reload before another heavy rebuild begins;
- `ApplyMapSnapshotAsync` has its own sequence and skips post-processing for superseded snapshots;
- `LoadSceneAsync` builds the next scene and loads SCO/SLI assets into local state before replacing `Scene`, `Picking`, and asset dictionaries;
- the continuation that commits/rebuilds D3D11 now preserves the caller context instead of using `ConfigureAwait(false)` before GPU work;
- the previous rendered scene stays intact until the next scene is ready to commit.

## New startup.log diagnostics

The log now records:

- ID and caller for every `ApplyMapSnapshotAsync`;
- concurrent apply count;
- ID for every `SetMapSnapshotAsync`;
- snapshots coalesced/cancelled by newer reloads;
- scene build start/end;
- SCO asset load time;
- SLI asset load time;
- object, spline, picking, terrain and auxiliary rebuild timing;
- GPU upload timing;
- final terrain/spline/object triangle counts;
- thread used for scene commit/rebuild.
