# OMSI Map Studio v0.2.0-alpha.5-test.10.38-native

Native preview focused on fixing apparently empty spaces at automatically generated junctions.

## Confirmed cause

In Test 10.36/10.37, the junction plan correctly calculated terrain height in `WorldPoint.Y`.

However, generated junction assets are regular scenery objects and do not use `[absheight]`. For these objects the renderer already adds local terrain height automatically.

Writing `WorldPoint.Y` into the object's Z value applied terrain height twice:

- object Z = terrain height;
- renderer added terrain offset again;
- the junction mesh could be rendered far above ground;
- road splines were still trimmed to reserve junction space;
- visually this produced a hole exactly where the crossing should be.

The log could still report every junction as inserted successfully because persistence was correct; the error was placement/render height semantics.

## Height fix

Procedural junctions are now stored with:

`relative Z = 0`

Final height is supplied only by terrain, matching OMSI scenery objects without `[absheight]`.

A regression test now uses a constant 12 m terrain and verifies that the mesh renders at about 12.102 m instead of roughly 24 m.

## Surface fitting

The generated junction surface is now approximately `0.102 m` above its local base.

This keeps the junction slightly above the road asphalt surface (`0.10 m`) within the controlled overlap area, avoiding z-fighting and visible seams.

## Same Road Kit asphalt

When the Road Kit is installed, junction generation copies:

`Splines\MapStudio_RoadKit\Texture\ms_asphalt.bmp`

into the junction asset.

Road and crossing therefore use the same procedural asphalt. A compatible procedural fallback remains available when the Road Kit texture is not present.
